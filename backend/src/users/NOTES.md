# `users` — notes

- **This module doesn't create accounts, `auths` does** — no `POST /users`. `UsersService.create()` is the low-level insert (receives `passwordHash` already computed as part of `NewUser`) and is only called from `AuthsService` — for public registration (`register`, always forces `Role.USER`) and for admin-created accounts (`adminCreate`, `POST /auths/admin-register`, lets an admin set `role`). `users` only manages accounts that already exist: read, update profile fields, delete. See `auths/NOTES.md` for the creation-side decisions.
- **`create()` itself doesn't pre-check email/name duplicates** — it relies on the table's `unique` constraints and lets the caller translate the Postgres `23505` violation into `ConflictException`, avoiding the classic check-then-insert race. `AuthsService`'s creation paths add the optimistic pre-check + `23505` catch around their own calls; `UsersService.update()` does the same for profile edits (see below).
- **`UserResponseDto`** (`dto/response-user.dto.ts`) uses `@Exclude()` at the class level + explicit `@Expose()` per allowed field (whitelist), not `@Exclude()` on `passwordHash` alone (blacklist) — a new sensitive column added to the table is excluded by default instead of leaking until someone remembers to blacklist it.
- **`UpdateUserDto` only has `name`/`email`/`photoS3Key`** — no `role`, no password field, for admin and self alike. It used to be `PartialType(CreateUserDto)`, which inherited `role`; combined with `PATCH /users/:id` being guarded only by `ResourceOwnerGuard`, a user could send `{ role: "admin" }` against their own id and self-promote — that was the actual bug this review closed, not just a missing implementation. A role change is treated as a separate, sensitive operation out of scope here (see `specs/users-crud.md`), and a password change needs its own flow that verifies the current password — neither belongs to this DTO. Since account creation moved to `auths`, `UpdateUserDto` no longer derives from a `CreateUserDto` in this module; it declares its three fields directly.
- **`SelfOrAdminGuard`** (`src/common/guards/self-or-admin.guard.ts`) is new: neither `RolesGuard` nor `ResourceOwnerGuard` alone expresses "owner OR admin", and Nest runs multiple `@UseGuards()` as AND, not OR, so they can't be composed on the same route to get this. Used on `GET /users/:id` and `PATCH /users/:id` so an admin can act on any user while a non-admin is restricted to their own id (same `OWNER_PARAM_KEY`/`'id'` default as `ResourceOwnerGuard`, for consistency).
- **Single-item endpoints only, not batch** — deliberate deviation from the `module-standards` batch-endpoint default (confirmed with the user). `users` handles credentials-adjacent data (email uniqueness on update) and has a use case (self-service profile) that is inherently single-item; forcing an admin-only batch surface alongside it would fragment the module's access model for no real benefit here.
- **Duplicate name/email on update**: `update()` catches Postgres `23505` and maps it to `409`, same pattern as `AuthsService`'s creation paths (see `auths/NOTES.md`).
- **Delete is a hard delete**: `favorites.userId` has `onDelete: 'cascade'` (`database/schema/favorite.schema.ts`), so removing a user removes their favorites too; nothing else FKs to `users` today (`listings` has no owner/seller column), so `remove()` never has to handle a blocking FK.
- **`photoS3Key` validation tightened** to the valid S3 object-key charset (`@Matches`) plus the column's `255` length, instead of a bare `@IsStringField()` — there's no upload module yet, so a real bucket-key convention (prefix, etc.) isn't invented here; this only rejects characters S3 keys can't contain.
- **Test scope**: covered in a separate testing session against `specs/users-crud.md`. `users.service.spec.ts` unit-tests `findAll`/`findOne`/`update`/`remove` against a mocked `DRIZZLE`. `users.controller.spec.ts` has two blocks: a unit block (mocked `UsersService`, delegation + response shaping) and an HTTP block that boots the controller with the real `JwtAuthGuard`/`RolesGuard`/`SelfOrAdminGuard`/`customValidationPipe` via `supertest` — that block is what actually exercises the privilege-escalation fix (`role`/`password` stripped from `PATCH` for both self and admin callers) and the admin-only-delete-even-for-self boundary, since a mocked service can't prove the real guard/pipe wiring holds. DTO boundary tests live in `dto/update-user.dto.spec.ts` and `dto/find-users.dto.spec.ts`.
