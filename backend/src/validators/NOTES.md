# `validators` — notes

See `docs/validation-error-codes.md` for the full design of the error-code system these validators plug into. This note covers implementation decisions specific to this directory.

- **`build-error-message.ts`** exists because `class-validator` only allows a `string` (or a function returning `string`) as an error message — there's no native way to attach structured data. `buildErrorMessage` encodes `{ code, meta? }` as JSON *inside* that string; `src/pipes/custom-validation.pipe.ts` is the other end that parses it back. Always serializes an array, even for a single item, so the consumer has one shape to parse.
- **`msg.ts`** is a thin convenience over `buildErrorMessage` for validators whose `meta` depends on the value being validated (e.g. `{ min, actual: args.value?.length }`) — in practice the wrappers below inline this pattern directly rather than using `msg`, but it's there for new validators that need it.
- **`normalize-text.ts`** (`normalizeForProfanityCheck`) lowercases, strips diacritics, strips punctuation, and collapses repeated characters (`"hooolaaaa"` → `"hoolaa"`) before the profanity check — `leo-profanity`'s wordlist is exact-match, so without normalizing, trivial evasion tricks (case mixing, accents, letter-stretching) would produce false negatives. Normalizing is more sustainable than trying to grow the wordlist to cover every variant.
- **`is-not-profane.validator.ts`**: only opines on content, not type — if the value isn't a `string`, `validate` passes and lets a type validator (`@IsStringField`) own that failure, avoiding duplicate/confusing errors on the same field. Doesn't take a `code` param like the wrappers do — always uses the generic `INVALID_TYPE`/`CONTAINS_PROFANITY` codes since there's no per-field variant the frontend needs to distinguish.
- **`is-not-markup.validator.ts`** (security-hardening finding, `specs/security-hardening.md` §5): rejects any `<`/`>` character in `name`/`email` (`RegisterDto`, `AdminCreateUserDto`, `UpdateUserDto`) and `description` (`CreateFragranceDto`, inherited by `UpdateFragranceDto` via `PartialType`) — stored-XSS potential for a future consumer (frontend, admin panel, email) that renders the field unescaped, confirmed dynamically pre-fix (`POST /auths/register` with `name: "<script>alert(1)</script>"` returned `201` and persisted it verbatim). **Rejects rather than strips**, same call `IsNotProfane` already made: a silent strip means the saved value differs from what was submitted with no error telling the caller why, which is worse than a `400`. Same structure as `is-not-profane.validator.ts` (opines on content only, passes through non-strings to `@IsStringField`), one new generic code `CONTAINS_MARKUP`. The `<`/`>` check is intentionally blunt (also catches harmless text like `"5 > 3"`) — the minimum bar the finding asked for, not an HTML parser; sufficient because these are short free-text fields (name, email, a product description) with no legitimate need for literal angle brackets.
- **`is-password-strong.validator.ts`**: a *composite* validator — `defaultMessage` returns an array of every failed rule's code (`PasswordErrorCode`), not just the first, because the frontend needs the full list to drive a "password requirements" checklist. Only `MIN_LENGTH` carries `meta` (`{ min, actual }`); the other rules are pure booleans.
- **`profanity.config.ts`**: `leo-profanity@1.9.0` ships no Spanish dictionary at all (`getDictionary()` silently falls back to `'en'` for any unregistered name), and `loadDictionary()` replaces the active word list rather than merging — so the previous code (`loadDictionary('es')` then `loadDictionary('en')`) never actually filtered Spanish; it always ended up with just English. Fixed by loading English via `loadDictionary('en')` and merging a Spanish list (`es-profanity-words.ts`, lowercase/diacritics-stripped to match `normalizeForProfanityCheck`'s output) additively via `add()`. That list was originally transcribed from a "listado de palabras malsonantes" reference doc (no longer in the repo; `es-profanity-words.ts` is the source of truth and nothing reads the original at runtime) plus a few Latin-American terms it didn't cover; `es-profanity-words.ts`'s own header documents known name-collision risks (e.g. "moña" normalizes to "mona", a common word/nickname) — whitelist via `leoProfanity.addWhitelist()` if one of those turns out to be a real problem, rather than deleting the entry. If a future `leo-profanity` release ships a real `es` dictionary, prefer switching to that over maintaining this list by hand.
- **Wrappers** (`wrappers/*`): each wraps a native `class-validator` decorator so its `message` carries a `{ code, meta? }` JSON payload instead of free text, with a sensible default `ValidationErrorCode`. `message` is a precomputed string when no `meta` is needed (`IsRequired`, `IsStringField`) and a function when `meta` depends on the value/args at validation time (`MinLen`/`MaxLen` expose `{ min/max, actual }`; `IsEnumField` exposes `{ allowed: Object.values(entity), actual }` so the frontend can list valid options without duplicating the enum).

- **`is-no-nul.validator.ts`** (QA finding on `specs/text-search-partial.md` rule 9): rejects a NUL byte in text query params. Postgres text cannot store NUL, so `?search=a%00b` used to reach the driver and return 500. Rejected (400, `CONTAINS_NUL_CHARACTER`) rather than stripped, same call as `IsNotMarkup`. Applied to every text filter that feeds a query (`FindFragranceDto`, `FindUsersDto`, `FindVendorsDto`). Body and params are covered by the global pipe below, not by this decorator; it stays on the query DTOs as defense in depth. `helpers/normalize-search-text.ts` is the `@Transform` that trims/collapses/de-duplicates `search` before `MaxLength`/`Matches` run (rule 7a/7b).

- **Request-wide NUL rejection** (`specs/nul-byte-rejection.md`, `helpers/find-nul-paths.ts`, `pipes/custom-validation.pipe.ts`): body DTOs used to be unprotected (`register`/`login`/every create/update could 500 on a `0x00`). Options weighed: (a) `@IsNoNul` on every string field, or (b) one check for the whole request. Chose **(b)**: `customValidationPipe` is a `ValidationPipe` subclass whose `transform` first deep-scans the raw body/query/param value (nested objects, arrays, object keys) and throws the same `errors[{field, errors:[{code:'CONTAINS_NUL_CHARACTER'}]}]` 400 before class-validator runs. Reasons: zero per-DTO surface, so a new DTO or a new string field is protected automatically (option (a) needs a reflection test to catch omissions and still misses `@Param`, un-decorated fields and batch items that are validated manually in services without `@ValidateNested`); it also fires before `@Transform`s and whitelist stripping, so the check sees exactly what was sent. Cost: one linear walk per request (body is capped at 256kb; depth capped at 64). Rejects rather than strips, as elsewhere. `mcp/tools/validate-dto-input.ts` calls the same helper because MCP input bypasses the HTTP pipe. Any code that validates a DTO outside `customValidationPipe` is only covered because the pipe already scanned the whole body first.
