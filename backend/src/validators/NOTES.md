# `validators` — notes

See `docs/validation-error-codes.md` for the full design of the error-code system these validators plug into. This note covers implementation decisions specific to this directory.

- **`build-error-message.ts`** exists because `class-validator` only allows a `string` (or a function returning `string`) as an error message — there's no native way to attach structured data. `buildErrorMessage` encodes `{ code, meta? }` as JSON *inside* that string; `src/pipes/custom-validation.pipe.ts` is the other end that parses it back. Always serializes an array, even for a single item, so the consumer has one shape to parse.
- **`msg.ts`** is a thin convenience over `buildErrorMessage` for validators whose `meta` depends on the value being validated (e.g. `{ min, actual: args.value?.length }`) — in practice the wrappers below inline this pattern directly rather than using `msg`, but it's there for new validators that need it.
- **`normalize-text.ts`** (`normalizeForProfanityCheck`) lowercases, strips diacritics, strips punctuation, and collapses repeated characters (`"hooolaaaa"` → `"hoolaa"`) before the profanity check — `leo-profanity`'s wordlist is exact-match, so without normalizing, trivial evasion tricks (case mixing, accents, letter-stretching) would produce false negatives. Normalizing is more sustainable than trying to grow the wordlist to cover every variant.
- **`is-not-profane.validator.ts`**: only opines on content, not type — if the value isn't a `string`, `validate` passes and lets a type validator (`@IsStringField`) own that failure, avoiding duplicate/confusing errors on the same field. Doesn't take a `code` param like the wrappers do — always uses the generic `INVALID_TYPE`/`CONTAINS_PROFANITY` codes since there's no per-field variant the frontend needs to distinguish.
- **`is-password-strong.validator.ts`**: a *composite* validator — `defaultMessage` returns an array of every failed rule's code (`PasswordErrorCode`), not just the first, because the frontend needs the full list to drive a "password requirements" checklist. Only `MIN_LENGTH` carries `meta` (`{ min, actual }`); the other rules are pure booleans.
- **`profanity.config.ts`**: `leo-profanity@1.9.0` ships no Spanish dictionary at all (`getDictionary()` silently falls back to `'en'` for any unregistered name), and `loadDictionary()` replaces the active word list rather than merging — so the previous code (`loadDictionary('es')` then `loadDictionary('en')`) never actually filtered Spanish; it always ended up with just English. Fixed by loading English via `loadDictionary('en')` and merging a Spanish list (`es-profanity-words.ts`, lowercase/diacritics-stripped to match `normalizeForProfanityCheck`'s output) additively via `add()`. That list is sourced from `malsonantes.md` (repo root — a markdown transcription of a "listado de palabras malsonantes" reference doc) plus a few Latin-American terms it didn't cover; `es-profanity-words.ts`'s own header documents known name-collision risks (e.g. "moña" normalizes to "mona", a common word/nickname) — whitelist via `leoProfanity.addWhitelist()` if one of those turns out to be a real problem, rather than deleting the entry. If a future `leo-profanity` release ships a real `es` dictionary, prefer switching to that over maintaining this list by hand.
- **Wrappers** (`wrappers/*`): each wraps a native `class-validator` decorator so its `message` carries a `{ code, meta? }` JSON payload instead of free text, with a sensible default `ValidationErrorCode`. `message` is a precomputed string when no `meta` is needed (`IsRequired`, `IsStringField`) and a function when `meta` depends on the value/args at validation time (`MinLen`/`MaxLen` expose `{ min/max, actual }`; `IsEnumField` exposes `{ allowed: Object.values(entity), actual }` so the frontend can list valid options without duplicating the enum).
