# `database` — notes

- **`DatabaseModule` is `@Global()`** with two chained providers: `PG_POOL` (internal, the raw `pg` Pool) and `DRIZZLE` (exported, the Drizzle-wrapped connection). `PG_POOL` exists as its own provider — rather than being created inline inside the `DRIZZLE` factory — specifically so it can be injected into the module and closed in `onModuleDestroy` (clean shutdown, no dangling Postgres connections in tests/redeploys).
- **`schema/index.ts` is the single source of truth** passed to `drizzle(pool, { schema })`, which is what enables Drizzle's query API (`db.query.fragrances.findMany({ with: { listings: true } })`) — and the same file `drizzle.config.ts` points at for migrations. If a new table/relation isn't re-exported from `schema/index.ts`, Drizzle doesn't know about it even though the table exists physically.
- **`drizzle.config.ts`** runs outside Nest's bootstrap (via the `drizzle-kit` CLI), so it loads `.env` manually (`import 'dotenv/config'`) instead of relying on `ConfigModule`.

## Schema quirks

- **`fragrances.id` is `uuid` (`defaultRandom()`)**; `users.id`, `vendors.id`, `listings.id` are `serial` (autoincrement). Any controller/service converting a route `:id` param with `+id` will get `NaN` against a fragrance id — watch for this when implementing `fragrances`.
- **`listings.fragranceId` column is physically named `"perfume_id"`**, not `"fragrance_id"` — the TS field and the Postgres column name don't match. Relevant when writing raw SQL or reading the schema directly.
- **`vendors.updatedAt` column is physically named `"updates_at"`** (with an "s"), inconsistent with every other table's `updated_at` — pre-existing naming inconsistency, not a typo to "fix" without a migration.
- **`listings` unique index `(vendorId, fragranceId, sizeMl)`**: a vendor can't have two listings for the same fragrance at the same size. The scraper is expected to upsert on this combination rather than insert duplicates — a violation here should become a `ConflictException` from the service layer, not a raw DB error. This predates `platform-spec.md` and initially conflicted with its §4.2 "one row per (fragrance, vendor)" wording; reconciled with the user by updating the spec (not the schema) — `platform-spec.md` §3/§4.2 now describe `Listing` as keyed by `(fragrance, vendor, size)`, since multi-size vendor offers are the real intended behavior.
- **`listings.price` is `integer`** (CLP has no subunit in practice), matching `platform-spec.md` §4.2's "precio actual (CLP, entero)" — not `numeric`, which would allow decimals that don't correspond to a real price a vendor charges.
- `users` itself has no FK columns to `fragrances`/`vendors`/`listings` — it's intentionally decoupled from the catalog/listing graph. The only link is via `favorites`, a separate join table (see below).
- **`favorites`** (`User`↔`Fragrance`, N:N — platform-spec.md §3/§5.4): both FKs (`userId`, `fragranceId`) are `onDelete: 'cascade'` — a favorite has no meaning once either side is gone, same reasoning as the `listings`→`fragrances` cascade in `fragrances-crud.md`. Unique index on `(userId, fragranceId)` prevents favoriting the same fragrance twice. Now that the module exists (`src/favorites/`), a violation surfaces as a per-item failure inside the batch response (`FavoritesService.createOne`), not a whole-request `ConflictException` — the batch-only mutation convention agreed for this module (`specs/favorite-module.md`) means the caller can favorite several fragrances in one request, so a duplicate has to fail only its own item, not the rest of the batch.
- **GIN/`pg_trgm` over a bigger B-tree on `fragrances.name` and `users.email`**: both columns are searched with a leading-wildcard `ilike('%term%')`, which a plain B-tree cannot serve at all (no fixed prefix to seek on — Postgres falls back to a full scan regardless of index size). Confirmed against a synthetic 300k-row `fragrances`/500k-row `users` dataset (`EXPLAIN ANALYZE`, see `specs/query-performance.md`): `Parallel Seq Scan` at 84-119ms dropped to `Bitmap Index Scan` at ~1-5ms after adding `CREATE EXTENSION pg_trgm` + `gin (col gin_trgm_ops)`. Deliberately *not* applied to `vendors.name`/`websiteUrl` (same `ilike` pattern) — that table is curated and stays at ~80 rows, where a `Seq Scan` already runs in well under a millisecond; a GIN index there would only add write/storage cost for no measurable read benefit.
- **`listings_vendor_id_idx` (single-column) dropped in favor of two composites**: `(vendor_id, price)` and `(vendor_id, id)` were added to serve `listings.findAll`'s vendor+price-range filter and the vendor-scoped keyset-pagination path respectively. By the leftmost-prefix rule, both composites already serve any plain `vendor_id` equality lookup the single-column index existed for, so keeping it around would only add write cost. Confirmed via `EXPLAIN` that no query in the codebase depends on the single-column index specifically before dropping it (every `eq(listings.vendorId, ...)` call site was grepped).
- **Migration uses plain `CREATE INDEX`, not `CREATE INDEX CONCURRENTLY`**: `drizzle-kit migrate` (`pnpm db:migrate`) wraps every pending migration file in one transaction (`drizzle-orm`'s `PgDialect.migrate`), and `CONCURRENTLY` cannot run inside a transaction at all. The migration file (`drizzle/0004_groovy_bug.sql`) documents the `CONCURRENTLY` DDL to run by hand via `psql` before applying it to a production database that already holds significant rows.
- **Drizzle wraps real driver errors — check `error.cause.code`, not `error.code`**: this drizzle-orm version (0.45.x) wraps every real Postgres driver error in a `DrizzleQueryError`, whose own `.code` is `undefined`; the actual Postgres error code (`23505` unique violation, `23503` FK violation, etc.) lives on `.cause.code`. `listings.service.ts`/`vendors.service.ts`/`fragrances.service.ts` all check `error.code` directly and so never actually detect a real constraint violation in production — confirmed by e2e tests against real Postgres (`listings.e2e-spec.ts`'s "KNOWN BUG" comments). `favorites.service.ts`'s `isUniqueViolation`/`getPgErrorCode` checks both `error.code` and `error.cause.code` for this reason; the other three modules still have the unfixed version and should be updated the same way if touched.
