# `auths` — notes

- **Session cookie (`SESSION_COOKIE_NAME` = `'session'`, `constants.ts`)**: `register`/`login` sign a JWT exactly as before (`buildAuthResponse`), but `AuthsController` now strips `accessToken` out of the response body and sets it as an httpOnly, `SameSite=Lax` cookie instead (`setSessionCookie`, via `@Res({ passthrough: true })`) — the body is just `{ user }`. `adminCreate` is unaffected (it never issued a token/cookie — see below). `JwtAuthGuard` reads the cookie as a fallback when there's no `Authorization: Bearer` header (see `src/common/NOTES.md`), so protected routes work for both a browser session and a raw API/Bearer client. This landed as the "not-yet-merged backend change" that `specs/auth-pages.md` ("Contract assumption") describes the frontend as having been built against — implemented directly in this worktree at the user's request during the `auth-pages` testing session (not the usual separate implementation session), so the frontend's assumption and this backend code were written independently and only reconciled here.
- **Double check on duplicate email in `AuthsService.register`**: `findByEmail` first (optimistic check, avoids hashing work if the email is already taken), *and* the `usersService.create(...)` call is wrapped in a try/catch that maps a Postgres unique-violation to `ConflictException` via `getPgErrorCode` (`src/common/utils/pg-error.util.ts`). The second check exists to cover the race between two concurrent registrations with the same email — without it, that race would surface as a generic 500 from an unhandled Postgres error instead of a 409. **Bug fixed 2026-09-14**: this previously checked `err.code === '23505'` directly, which never matches — drizzle-orm wraps the real pg error under `err.cause`, so the check silently always fell through to `throw err` (a raw 500). Concretely, this broke registering with a `name` that's already taken (`users.name` has its own unique constraint, unlike `email` there's no optimistic pre-check for it) — every other service module already had the correct `.cause`-aware version, `auths` was the one holdout. Now uses the shared `getPgErrorCode` util. Residual (not fixed, out of scope of that bug fix): the `ConflictException` message is hardcoded `'Email already registered'` regardless of whether `email` or `name` was the actual duplicate, and the frontend's `RegisterForm` (`specs/auth-pages.md`, "/register") always renders a 409 as the email field's "Ese correo ya está registrado." — so a duplicate-*name* registration attempt now correctly gets a 409 instead of a 500, but still shows a misleading "email already registered" message under the wrong field. Flagged, not fixed — would need both a backend message/field distinction (email vs name) and a matching frontend change beyond what the spec currently describes.
- **Generic login error on purpose**: both "email doesn't exist" and "wrong password" return the same `UnauthorizedException('Invalid email or password')` — deliberately not distinguishing the two, so a failed login can't be used to enumerate registered emails.
- **`role` never comes from an unauthenticated client**: `RegisterDto` has no `role` field; `AuthsService.register` always forces `Role.USER` explicitly on create, so public registration can never self-assign `admin`. The only path that can set `role` is `POST /auths/admin-register` (`AdminCreateUserDto` → `AuthsService.adminCreate`), guarded by `JwtAuthGuard` + `RolesGuard(Role.ADMIN)`. `RegisterDto`/`LoginDto`/`AdminCreateUserDto` reuse the same `ValidationErrorCode`s for `name`/`email`/`password` — one source of truth for what those fields mean to the frontend, regardless of which endpoint they came through. `LoginDto` intentionally skips `@IsStrongPassword()` (login isn't the place to validate strength — that already happened at registration).
- **Account creation is entirely owned by `auths`, including admin-created accounts** — `users` only manages accounts that already exist (read/update/delete). `adminCreate` doesn't return an `accessToken` like `register`/`login` do: the admin calling it isn't the account logging in, so there's no session to hand back, just the created `UserResponseDto`.
- **`JwtConfigModule` is separate from `AuthsModule`** and `@Global()`, so any future module needing to sign/verify tokens doesn't have to depend on `auths`. Uses `registerAsync` because `secret`/`expiresIn` come from `ConfigService`, which needs async resolution.
- **`login` returns `200`, not the `201` default for `POST`** (`@HttpCode(HttpStatus.OK)` in `AuthsController`) — a successful login doesn't create a resource.
- Follows the repo's error-handling convention (`docs/error-handling.md`): built-in Nest exceptions only, no custom hierarchy.
- **Test scope** (`auths.service.spec.ts`/`auths.controller.spec.ts`): `register`'s optimistic duplicate-email check is covered; its `code === '23505'` race-condition branch is not — no dedicated test for it in this file. `adminCreate` has both: the optimistic duplicate-email check, and a dedicated test for the `23505` branch (a duplicate *name* with a fresh email, since the optimistic check only looks at email). `auths.controller.spec.ts` also has an HTTP block that boots `POST /auths/admin-register` with the real `JwtAuthGuard`/`RolesGuard(ADMIN)`/`customValidationPipe` — the only route that can mint an admin account, so its guard is exercised for real rather than only asserted via a mocked service.
